# Rencana Modul 11

Targetnya menyelesaikan spesifikasi modul dan laporan D.1–D.4 dengan kode yang mudah dibaca. Kerjakan satu tahap per sesi. Baca bagian tahap ini, kode yang terkait, dan halaman modul yang diperlukan.

## Aturan untuk agent

- Mulai dari tahap pertama yang belum dicentang. Periksa keadaan repo sebelum mengedit. Kalau pilihan penting tidak bisa dipastikan dari repo atau modul, ajukan satu pertanyaan yang spesifik. Untuk keputusan kecil, ikuti pola repo.
- **Satu langkah praktikum = satu giliran chat.** Agent mengedit satu file atau menjalankan satu perintah, lalu tutup giliran dengan penjelasan singkat tentang perubahan atau hasil, tujuan, dan satu langkah berikutnya. Tunggu balasan eksplisit seperti “lanjut”. Penjelasan di tengah giliran tidak menggantikan jeda. Pemeriksaan baca saja boleh dilakukan untuk menyiapkan langkah. Saat pengguna sedang bertanya atau evaluasi, jawab dan tunggu instruksi lanjut. Aturan ini berlaku juga pada penulisan laporan, pembaruan progres, dan chat baru.
- **Agent menjalankan perintah persiapan dan pemeriksaan rutin. Pengguna menjalankan perintah untuk bukti praktikum.** Untuk `go build`, `go test`, `go vet`, atau uji runtime yang dipakai sebagai bukti, berikan satu perintah siap salin, sebutkan terminal dan bagian output yang perlu terlihat, lalu tunggu hasil dari pengguna. Jika perintah persiapan seperti `go get` mengubah `go.mod` dan `go.sum` otomatis, jelaskan keduanya sebagai hasil dari satu perintah. Tetap lakukan edit manual satu file per langkah.
- **Untuk uji API, pakai HTTPie.** Cek method, URL lengkap (termasuk prefix `/api/v1`), port, auth, dan body dari route aktif. Beri satu request per giliran. Minta hanya status dan field yang relevan, tanpa token atau kata sandi. Jika kode server atau worker berubah, pandu restart proses yang sesuai sebelum uji ulang.
- **Rumpang maksimal satu potongan kecil di satu file per tahap.** Saat sampai di sana, tunjukkan file, fungsi, baris yang harus diganti, dan hint yang menyebut API atau pola yang dipakai. Kalau pengguna bilang bingung, jelaskan dengan contoh kecil atau tampilkan potongan pengganti agar pengguna bisa menempelkannya sendiri. Agent hanya mengisi langsung jika diminta. Pisahkan pekerjaan pengguna dari perubahan pendukung yang dibuat agent.
- Ikuti struktur repo. Gunakan solusi paling sederhana yang memenuhi modul. Kalau uji gagal, telusuri satu penyebab, perbaiki, lalu ulangi uji terkait. Tunda perapian yang tidak memengaruhi hasil wajib.
- Pisahkan error dari kode rumpang atau adaptasi repo dari sembilan bug bawaan modul. Untuk bug bawaan, ikuti urutan ini: **pengguna menjalankan uji → pengguna mengambil screenshot hasil gagal → agent menunggu konfirmasi bukti sudah diambil → agent menjelaskan gejala, akar masalah, dan usulan perbaikan → perbaiki satu file → pengguna mengulang uji yang sama**. Jika bukti sesudah diperlukan, minta screenshot hasil ulang. Catat hasil aktual di `laporan.md`. Jika uji ternyata lulus, laporkan hasilnya dan periksa penyebabnya bersama pengguna.
- Sebelum memberi perintah uji, nyatakan apakah screenshot diperlukan. Untuk bukti bug, sebutkan nilai yang benar dan gejala yang dicari, lalu gunakan perintah atau request yang sama sebelum dan sesudah perbaikan. Minta screenshot saat hasil masih terlihat. Sebutkan bagian yang harus terlihat, caption sesuai hasil aktual, dan lokasi tempel di Word. Screenshot setup rutin atau potongan kode cukup dilewati kecuali diperlukan sebagai bukti.
- Saat ada hasil yang layak masuk laporan, perbarui `laporan.md` dengan narasi siap salin dan penanda gambar, misalnya **[C2-01 — Tempel di D.3 → C.2 setelah hasil saat Redis mati. Tampilkan outbox_pending dan queue_error.]** Pengguna menempel screenshot sekali, langsung ke Word. Jika diminta merapikan Word, edit dokumen yang ada agar gambar tetap tersimpan. Catat progres operasional di bawah ini.

Salin narasi ke draf Word, lengkapi identitas, tautan repo, dan gambar, lalu ekspor `Tugas11_NIM.pdf`. **Selesai saat** kode dan laporan siap dikumpulkan. Keluarkan `.env` dan folder `logs/` dari pengumpulan.
